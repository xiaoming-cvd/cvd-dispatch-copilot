**版本**：v1.1（按总工评审意见修订）
**日期**：2026-10-12
**作者**：城配调度副驾开发组
**评审人**：总工程师
**状态**：通俗演示版第一期已实现并纳入 354 项测试基线；本版已按评审意见完成 P0/P1/P2 修订

## 一、背景与问题

当前工作台呈现的是**基于公开基准数据（Solomon / Kilby）构建、测试和评估**的工程
数据：订单 ID（o90）、车辆 ID（V1）、时间（模型行驶秒）、诊断 JSON。这对专业审查
完全正确，但对三类人构成门槛：

1. **不懂物流的外行**（比赛评委、参观者、潜在客户）：看不懂 ID、矩阵和"相邻破坏数"；
2. **一线调度员**：没时间读诊断 JSON，需要"一句话结论 + 一张图"；
3. **未来的真实地图接入**：Solomon/Kilby 是基准算例，未来接真实 GIS 地图、真实车队
   （异构车型、多趟、司机工时）后，复杂度只会更高——**如果每次复杂度上升都再做一遍
   "翻译简化"，呈现层会不断重写，不可持续**。

因此需要一套**稳定的双模式架构**：同一套数据，两种呈现。复杂度上升时，专业版承接
全部细节，通俗演示版只承诺"看得懂的结论"，而不是每次重做翻译。

## 二、总体设计：三层分离

```
┌─────────────────────────────────────────────┐
│ 呈现层（两种模式，可一键切换，互不污染）        │
│  专业审查版：表格 / 算式 / 候选池 / 原始 JSON   │
│  通俗演示版：大白话故事 / 座位图 / 散点图       │
├─────────────────────────────────────────────┤
│ 语义映射层（纯展示，新增，不动数据）            │
│  ID→演示称谓（确定性生成）/ 顺序图标记         │
├─────────────────────────────────────────────┤
│ 数据层（完全不动）                            │
│  场景 / 求解结果 / 诊断记录 / 原始 ID / 模型秒  │
└─────────────────────────────────────────────┘
```

**四条铁边界**：

1. 映射层只做"翻译"，**不改数据、不改算法、不改评测口径**；
2. 原始 ID 在所有通俗演示版图表中**悬停可查**（顺序图标记、时刻表单元格均有
   `title=原始 ID`），并可一键导出"演示称谓对照表"（含场景 ID/版本/输入哈希/
   映射算法版本）供审查核对翻译忠实性；
3. 时间一律保留"模型行驶秒"，**不换算真实分钟、不换算人民币**（既有红线）；
4. 评测、报告、审查全部走**专业审查版口径**，通俗演示版不进任何评测链路。

## 三、通俗演示版第一期（已实施）

| 组件 | 做法 | 外行视角的效果 |
|---|---|---|
| 演示称谓 | 订单→"演示A组·站点07"、车辆→"1号车"。按（场景ID+原始ID）fnv1a 哈希确定性生成，同一场景每次打开名字相同、可复现。**刻意不使用暗示真实的词库**（小区名/姓氏），并常驻注明"示意称谓不代表实际地理/客户/人员/业务含义" | 看到"演示C组·站点42"而不是"o90"，同时知道这只是代号 |
| 大白话决策故事 | 固定模板拼真实数字（无大模型参与）：insert="试了 18 个空位、17 个会让客户超时、只有 1号车 第 3 个位置合适"；低扰动="推荐的不是总时间最低的（要多换 3 辆车），而是 0 换车的——原计划已下发，稳定比单纯省时间值钱" | 零术语读懂"系统为什么这么决定" |
| 座位图 | 每张新单一排色条：绿=能放、红=被拒（超时/超载）、★=选中的车 | "为什么这张单只能上那辆车"不用再解释 |
| 候选散点图 | 横轴=模型行驶秒、纵轴=换车订单数、**颜色=相邻顺序破坏数**（角色用形状区分：绿双圈=推荐、蓝方块=池内最低成本）；虚线=成本上限，直接标注算式"1.10 × 35412 = 38953 模型秒" | "为什么不选总时间最低的那个"图上自己说话 |
| 三方法比较 | 版本/输入哈希/请求预算三门控 + 规则生成选法建议 | 一键三方法后自动对照，杜绝口径混排 |

**验证状态**：354 项测试全绿；insert 枚举计数（每车槽位可行数）、低扰动种子
统计（insert/relocate 尝试与找到数）已端到端冒烟；决策面板全部数据来自运行
记录的一次性快照（事后回放），无编造、无二次求解。

## 五、未来接真实地图/真实车队时的演进路线

回答"复杂度上升后怎么办"：**不需要再做一遍翻译，只做三次"源替换"**。

| 层 | 现在（第一期） | 未来（真实接入） | 改动点 |
|---|---|---|---|
| 布局源 | 顺序图（原计划→新计划并排） | 真实经纬度地图（adapters 已能解析 Solomon 坐标、Kilby 真实坐标；物化层加可选 `coords` 字段） | 后端物化 + schema 可选字段；前端新增地图组件 |
| 命名源 | 演示称谓池（哈希分配，中性词库） | 真实客户名/POI，由数据方提供**白名单映射表**（映射表本身入档可审计）；敏感名走脱敏规则 | 映射层增加"外部映射表"输入，展示组件不变 |
| 车辆源 | 编号 | 车型/载重/冷链/多趟/司机工时等真实属性进**专业版字段**；通俗演示版每辆车只取 1-2 个关键属性（如"冷链车"），其余折叠 | 专业版表格加列；演示版卡片配置化 |

**复杂度治理原则**（复杂度上升时通俗演示版不重写的保证）：

1. 通俗演示版**只承诺三件事**：结论是什么、为什么这么定、动了谁的路线；其余一律
   "详情折叠"而非删除；
2. 新增复杂概念时，先问"外行需要知道吗"——不需要就只进专业版；需要就给一个
   **比喻**（如多趟运输="同一辆车一天跑两圈"），比喻进固定模板词库，程序拼装，
   不允许大模型现场发挥；
3. 任何真实数据接入后，**双口径标注**保留（如"模型秒 / 实测 GPS 里程"并列），
   报告不直接换算人民币。

## 六、工程约定

1. **模式开关**：首次访问双入口自选；页头按钮一键切换，选择记忆在浏览器本地；
   切换保留当前场景、任务与滚动位置，不重新求解；
2. **诚实标注**：演示称谓常驻免责声明；故事面板标"事后回放 · 真实运行记录生成"；
   求解状态口径（可行≠最优、超时≠不可行）两种模式完全一致；
3. **审查路径不受损**：通俗演示版下 JSON 下载、原始 ID（悬停）、独立校验结果、
   称谓对照表导出与专业版完全一致；
4. **单一数据源**：两种模式读取同一份结果对象，杜绝"两套数"；
5. **性能**：呈现层全部为 O(候选数) 的 DOM/SVG 渲染，无重计算；不做"毫秒级"
   预称，真实性能以实测为准（当前 39 场景规模下无感知延迟）。
